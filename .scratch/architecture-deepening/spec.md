# 架构深化与存量数据安全

Status: ready-for-agent  
Date: 2026-11-10

## Problem Statement

当前产品把文件备份、数据库备份和离线介质的复杂执行流程分散在重复 runner、静态工具和不完整的状态 helper 中；网站又把客户授权、订单、服务商、结算、开票和产品写入直接组合在大型 controller 和启动代码里。调用者需要知道过多顺序、持久化时点和副作用，导致同一条规则多处维护，也难以从最高业务入口完整测试。

网站已有客户信息和订单数据，本地数据库快照包含 20 张业务表、客户、订单、授权、设备、支付和历史产品。当前 schema 依赖启动时原地建表、加列和 seed，且工作区快照的 `AdminUsers.Email` 索引一致性异常。架构调整如果改变主键、订单金额、支付状态、授权到期日、设备记录、佣金历史或开票关联，将造成不可接受的业务损失。

## Solution

按阶段深化 module，保持现有业务行为和存量数据含义不变。

阶段 0 建立生产数据库只读预检、部署备份、关联检查、行为基线和兼容测试夹具；阶段 1 优先收拢文件备份、MSSQL 备份和 MySQL 备份的运行 lifecycle；之后依次深化客户端网站会话、厂商运营写入、网站数据库启动、云去向和离线介质运行。

任何阶段都不得为了拆 module 而重写客户、订单、支付、授权、设备、服务商、佣金、结算、开票和产品历史。每个涉及网站的发布必须先证明旧数据、活动会话、已下架产品和历史订单仍能按原语义读取。

## User Stories

### 存量账号

1. 作为现有客户，我希望升级后仍能用原登录邮箱登录，以便账号身份不变。
2. 作为现有客户，我希望姓名、昵称、公司、手机和开票资料保持不变，以便后续开票和识别不受影响。
3. 作为已付款客户，我希望订单号、金额、支付时间、渠道和支付状态保持不变，以便财务记录可追溯。
4. 作为已退款客户，我希望退款状态、时间和订单关联保持不变，以便售后记录不对账错乱。
5. 作为现有客户，我希望授权到期日、宽限期、授权来源、发放原因和定制版设备上限保持不变，以便客户端判断不漂移。

### 设备与运营

6. 作为现有客户，我希望已占用设备和有效会话在部署后继续有效，以便升级不要求全量重新登录。
7. 作为被踢出的客户，我希望已作废的设备令牌继续保持失效，以便安全边界不倒退。
8. 作为服务商，我希望直属客户、等级、佣金比例快照、佣金明细和结算关联保持不变，以便历史可核对。
9. 作为厂商，我希望开票申请与订单、客户开票资料之间的关联保持不变，以便不重复或丢失开票记录。
10. 作为厂商，我希望产品价格、促销窗口、设备上限、上下架状态和历史旧产品保持不变，以便历史订单仍可解释。

### 备份运行

11. 作为文件备份用户，我希望单 ZIP 和分卷备份包继续按现有规则复用或重新打包，以便升级不重复上传大包。
12. 作为数据库备份用户，我希望多个数据库仍独立记录完成状态，以便部分失败只补传未完成项。
13. 作为备份用户，我希望网络、FTP、云、邮件和立即删除的现有结果含义保持不变，以便升级不改变成功或失败判断。
14. 作为备份用户，我希望旧的未传完的备份记录继续可读，以便历史单 ZIP 和分卷备份能够完成。
15. 作为运维人员，我希望文件、MSSQL 和 MySQL 备份从同一运行入口得到一致行为，以便一次修复覆盖全部来源。

### 客户端网站会话

16. 作为客户端用户，我希望密码登录和邮箱验证码登录保持现有行为，以便升级不改变登录方式。
17. 作为达到设备上限的用户，我希望仍收到设备上限和踢出或升级引导，以便不会误以为授权丢失。
18. 作为网络不稳的用户，我希望网站暂时不可达时沿用现有授权宽限判断，以便正常备份不被短暂断网阻断。
19. 作为设备被换机或被踢出的用户，我希望客户端仍会清除失效会话并要求重新登录，以便不会沿用错误设备身份。
20. 作为开发者，我希望网站会话能在不启动 WPF 窗口的情况下测试，以便网络和持久化错误不再只靠人工验证。

### 厂商运营

21. 作为厂商，我希望发放授权、修改账号类型和删除客户继续满足当前权限与校验规则，以便后台操作可预测。
22. 作为厂商，我希望修改产品价格、促销、设备上限和上下架时继续留下操作证据，以便审计历史不中断。
23. 作为厂商，我希望审批服务商、调整等级、冻结服务商、审批结算和付款保持原语义，以便运营流程不被打断。
24. 作为厂商，我希望客户搜索、看板、设备和日志使用同一业务规则，以便页面之间不出现状态差异。
25. 作为开发者，我希望厂商写入规则集中测试，而不是通过大型 controller 间接覆盖，以便新增操作时不必复制查询和事务顺序。

### 网站数据库启动

26. 作为运维人员，我希望部署前自动检查数据库完整性和关键关联，以便发现异常时主动停止。
27. 作为运维人员，我希望每次修改网站数据库都有可恢复备份和明确回滚方式，以便失败时恢复原服务。
28. 作为现有客户，我希望升级只做必要增量变更，不重写、不重新编号、不重建现有业务表，以便历史关联稳定。
29. 作为运维人员，我希望启动升级可重复执行并报告 schema 版本，以便半途失败后可安全重试。
30. 作为产品维护者，我希望已下架旧产品继续保留，以便历史订单仍能解析产品，而不是依赖当前销售目录。

### 云与介质

31. 作为云备份用户，我希望五个云服务商继续使用统一的对象名、整组清理和上传校验规则，以便安全要求一致。
32. 作为云备份用户，我希望七牛云、百度网盘、阿里云、腾讯云和天翼云只保留签名、分页和 HTTPS 协议差异，以便整组规则只维护一处。
33. 作为离线介质用户，我希望计划执行和手动执行继续遵守窗口、等待、介质登记、写入、清理和离线的现有顺序，以便安全属性不退化。
34. 作为使用卷离线或整盘离线的用户，我希望设备不支持整盘离线时仍按现有规则回退，以便失败不会变成格式化或误删。
35. 作为维护者，我希望云去向和离线介质的高风险顺序可通过 adapter fake 测试，以便不依赖真实账号或移动盘即可回归。

## Implementation Decisions

### 阶段顺序

- 阶段 0：建立生产数据库只读预检、部署前备份、关联完整性检查、行为基线和脱敏兼容夹具。
- 阶段 1：深化文件备份、MSSQL 备份和 MySQL 备份共用的运行 lifecycle；不修改网站数据库。
- 阶段 2：深化客户端网站会话；不改变网站账户、订单或授权 schema。
- 阶段 3：深化厂商运营写入 module；controller 只保留认证、请求和响应适配。
- 阶段 4：深化网站数据库启动与升级 module；进入前必须完成生产数据副本演练。
- 阶段 5 和阶段 6：依次深化云去向和离线介质运行 module。

### 已确认 seam

- 唯一外部 seam 是单任务执行入口；任务存储成功抢占运行锁后调用它，调度循环、计划计算和命令分发留在 lifecycle module 外。
- 单任务执行入口一次覆盖复用判断、重打包替换、分卷、逐文件通道进度、持久化、上传校验、通知、立即删除、结果码和日志。
- 文件、MSSQL 和 MySQL 来源 adapter 只准备来源快照、生成一个或多个备份包并返回运行统计，不推进待传状态、不发送通知、不删除备份。
- 三类任务表继续使用各自现有的 `pending_json`；由任务存储 adapter 读取和保存，不迁移线上已有未传完的备份记录。
- `ExecuteDue`、运行锁和来源分发保持在 lifecycle 外；完整 lifecycle 只在单任务 seam 内组合。

### 第一阶段交付

- 先建立统一 lifecycle module 和 fake 来源测试，再依次切换文件备份、MSSQL、MySQL，每次只替换一个生产来源。
- 第一阶段只保持现有行为，不改变多通道继续尝试、邮件失败为 `warn`、跳过文件导致数据失败、删除失败保留重试证据等规则。
- 第一阶段不连接或修改生产网站数据库；它只触及本机备份数据库和备份文件。
- 会修改网站数据的后续阶段仍必须等待生产库只读预检、一致备份和副本迁移演练完成。
- 总规格保留六阶段安全边界；阶段 1 单独形成实现工单，后续阶段随前序验收再拆。

### 存量数据不可变条件

- 默认保持现有表名、列名、主键、订单号、客户号、授权到期日、支付状态和金额语义不变。
- 不为模块拆分批量重写客户、订单、支付、授权、设备、服务商、佣金、结算、开票和产品记录。
- 迁移只允许可解释、幂等、向前兼容的增量变更；同一部署不得删除旧列、旧表或历史产品。
- 每次触及网站数据库的发布都必须生成一致备份，并在独立副本完成入口级兼容测试和回滚演练。
- 预检至少检查表结构、行数、主要唯一键、逻辑外键、已付款金额、有效授权、活动设备、历史佣金和开票关联；报告不得包含密码、令牌、密钥或客户明细。

### 备份运行 lifecycle

- 文件、MSSQL 和 MySQL 备份共享一个深 module，负责复用判断、重打包替换、分卷、逐文件通道进度、持久化、上传校验、通知、立即删除和结果码。
- 文件源和两类数据库实例只提供“如何产生一个或多个备份包”的窄 adapter。
- 单 ZIP、分卷备份包、未传完的备份和旧待传记录继续可读；不改变 ADR-0002 的分卷格式。
- 网络、FTP、云和邮件失败语义保持；邮件失败仍只影响通知状态。
- 删除仍按备份单元执行；部分删除失败必须保留可重试证据。

### 网站与客户端 module

- 客户端网站会话 module 吸收 HTTP、结构化响应解析、令牌与会话持久化、授权摘要和设备一致性；WPF 登录窗口只作为 UI adapter。
- 不再使用正则表达式解析网站 JSON；协议类型由 HTTP adapter 返回。
- 厂商运营按“客户与授权”“服务商与等级”“结算与开票”“产品与价格”四个业务概念收拢写入规则。
- 网站数据库启动 module 负责 schema 版本、有序增量升级、目录 seed 和管理员初始化；composition root 只调用一次升级。
- 旧产品、旧订单、旧授权和旧开票必须可解析，不得用当前销售目录替代历史产品记录。

### 云去向与离线介质

- 云去向深 module 负责上传恢复、远端存在性校验、整组过期判断、删除顺序和进度日志；五家 adapter 保留签名、分页和协议差异。
- `ICloudStorage` 是已有 seam；不引入官方 SDK，不违反 ADR-0001。
- 云清理只处理产品前缀下的备份包对象；分卷和分卷清单作为同一单元处理。
- 离线介质运行 module 吸收窗口、等待、登记校验、打包、复制、版本清理、卷离线和整盘离线；磁盘与文件系统作为内部 adapter。
- 离线介质不受网站授权影响；等待、跳过和失败都必须可审计。

### 开发与发布

- 先修复 solution 引用不存在测试项目的构建断裂，再开始任何阶段。
- 为备份运行 lifecycle 新建聚焦测试工程并更新 solution，不恢复当前已删除且混有无关历史用例的旧测试工程。
- 每个阶段先保持旧入口可用，再替换内部实现；禁止一次同时替换数据格式、协议和 UI。
- 每次修改只引入一个外部测试 seam；内部需要多个 adapter 时保持私有，不扩大调用者 interface。
- 新 module 接受时钟、持久化和外部 I/O 依赖，不在内部创建真实网络、进程或设备依赖。
- 变更日志只记录版本、迁移编号、行数级别检查结果和失败阶段，不记录敏感值。

## Testing Decisions

- 测试从用户可观察行为或最高业务入口进入，不验证私有方法、SQL 字符串、日志内部顺序或具体 adapter 类型。
- 备份运行 lifecycle 的唯一测试组合是临时 SQLite、假文件源、假 MSSQL/MySQL 源、假网络/FTP/云/邮件；同时提供旧单 ZIP、旧未传完的备份和历史分卷记录夹具。
- 运行锁、`ExecuteDue` 和计划计算在独立任务存储测试中验证，不通过完整 lifecycle 测试入口重复覆盖。
- 日志测试只冻结结果码和用户可理解的关键消息，例如“存在跳过文件”“云上传失败”“邮件失败”，不逐字锁定完整日志。
- 数据兼容测试使用脱敏或合成的生产结构副本，验证迁移前后客户、订单、支付、授权、设备、服务商、佣金、结算、开票和产品的主要查询返回相同语义。
- 备份 lifecycle 首选现有任务执行入口和临时 SQLite，搭配文件、数据库源、网络、FTP、云、邮件 fake；相似先例是现有文件备份统计、分卷、待传记录和云恢复测试。
- 网站测试使用临时数据库并走 HTTP 入口，覆盖厂商登录、客户搜索、授权发放、改账号类型、产品修改、服务商冻结、结算和开票。
- 云去向测试使用 `ICloudStorage` fake 验证分页、整组过期、清单最后删除和失败中止；离线介质测试通过盘与复制 adapter fake 验证等待、不可写拒绝、成功后清理和失败仍离线。
- 必须保留至少一个包含已下架旧产品、部分客户资料、无服务商订单、有效授权、已踢设备和历史佣金的兼容测试夹具。
- 预检测试覆盖索引异常、逻辑孤儿、重复唯一键、已付款金额异常和中断后重试；生产预检失败时停止部署，不自动修复。
- 源码字符串断言只能补充确认入口存在，不能代替模块行为测试。

## Out of Scope

- 改变产品价格、退款窗口、授权宽限期或设备上限规则。
- 改变分卷备份包格式、云对象命名、上传分片算法或密码算法。
- 增加云空间下载、增量备份、去重、版本浏览或新云服务商。
- 在架构深化过程中清理、归档或批量修正现有客户和订单数据。
- 读取或提交生产密码、令牌、云密钥、支付密钥和客户明细。

## Further Notes

- 本规格未直接连接生产服务器；阶段 0 必须在实际服务器持久化数据库上执行只读预检和一致备份。
- 工作区快照有 20 张业务表，包含 2 个客户、1 个订单、2 条授权、2 台设备和 5 个产品；逻辑关联检查未发现孤儿，但 `AdminUsers.Email` 索引返回一致性异常，不能忽略。
- 快照中保留了已下架旧产品；脱敏夹具应保留这种历史形态。
- 当前 solution 引用了已不存在的两个测试项目；CloudRecovery 测试单独通过 41 项，该构建断裂必须在阶段 0 修复。
- “备份运行”已加入领域词汇；实现和测试使用该词描述一次完整备份过程。
