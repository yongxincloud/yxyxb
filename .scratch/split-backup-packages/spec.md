# 分卷备份包与运行统计

Status: ready-for-agent

## Problem Statement

当文件备份任务包含大量文件时，用户看不到本次实际准备了多少文件、总数据量以及是否有文件被跳过。程序会把所有可读文件压成一个很大的 ZIP；这个 ZIP 作为单个对象上传时，失败影响整个包，重试成本高，用户也很难从云空间下载、核对和恢复。

数据库备份也面临同样的大包上传问题。用户完成备份后，邮件没有本次文件数量、分卷数量和大小统计；程序当前也没有根据下载后的多个分卷自动组装和恢复原始文件的流程。

## Solution

在生成备份包前统计发现文件数、可打包文件数、跳过文件数和源数据大小。先生成完整 ZIP；未超过分卷上限时继续使用单 ZIP，超过上限时按固定字节区间切成多个独立 ZIP 分卷。

每次分卷备份包含一个外部 `manifest.json` 和每个分卷内部的内嵌清单。清单记录备份标识、分卷顺序、大小、哈希和运行统计。程序先上传分卷，最后上传外部清单；每个文件分别记录网络共享、FTP 和云通道是否成功，失败重试只补传未完成项。

所有启用的数据通道都完成上传和校验后，才把数据状态判定为成功。邮件失败显示“备份成功，通知失败”。邮件增加文件、分卷和大小统计变量。

用户从云空间手工下载同一次备份的全部分卷和清单，放入同一目录后，在客户端选择该目录即可校验、组装和恢复。恢复结果写入带时间戳的新目录，不覆盖已有文件。程序不提供云空间下载。

## User Stories

1. 作为文件备份用户，我希望任务开始前统计要处理的文件数量，以便知道本次备份规模。
2. 作为文件备份用户，我希望看到发现文件数、实际打包文件数和跳过文件数，以便发现备份不完整。
3. 作为文件备份用户，我希望看到源数据总大小，以便评估磁盘和上传需求。
4. 作为文件备份用户，我希望锁定或无权限的文件被明确列出，以便修复权限或关闭占用程序后重试。
5. 作为文件备份用户，我希望存在跳过文件时任务判定失败，以便不会把不完整备份误认为成功。
6. 作为文件备份用户，我希望即使存在跳过文件也继续处理可读文件，以便本次尽可能完成备份并保留失败证据。
7. 作为文件备份用户，我希望 ZIP 写入设置中的备份目录，以便所有备份产物集中管理。
8. 作为文件备份用户，我希望较小的备份继续使用单个 ZIP，以便保持简单和兼容。
9. 作为文件备份用户，我希望超过上限的 ZIP 自动拆成多个分卷，以便降低单个云对象上传失败的影响。
10. 作为文件备份用户，我希望全局默认单个分卷上限为 4 GiB，以便无需配置即可使用。
11. 作为文件备份用户，我希望全局允许修改分卷上限，以便适配不同云服务商。
12. 作为文件备份用户，我希望任务可以继承全局值或单独覆盖，以便特殊任务有不同大小限制。
13. 作为文件备份用户，我希望每个分卷都是有效 ZIP，以便可以单独检查文件是否可打开。
14. 作为文件备份用户，我希望外部清单和每个分卷内的清单记录顺序与哈希，以便恢复时自动识别和安全校验。
15. 作为文件备份用户，我希望外部清单丢失时仍能从分卷内嵌清单恢复，以便减少漏下载造成的失败。
16. 作为文件备份用户，我希望分卷按编号依次上传，以便云端目录容易理解。
17. 作为文件备份用户，我希望某个分卷失败后只补传未成功的分卷和通道，以便避免重复上传整个备份。
18. 作为文件备份用户，我希望清单最后上传，以便清单出现时对应分卷已经上传。
19. 作为文件备份用户，我希望程序确认云端对象存在且大小正确，以便上传成功不等于文件完整。
20. 作为文件备份用户，我希望只有全部启用通道和全部分卷都成功时数据状态才成功，以便结果可信。
21. 作为邮件接收者，我希望看到发现、打包和跳过文件数，以便判断文件是否完整。
22. 作为邮件接收者，我希望看到分卷总数和上传成功数，以便判断所有文件是否上传完成。
23. 作为邮件接收者，我希望看到源大小、压缩后大小和已上传大小，以便识别异常压缩或上传。
24. 作为邮件接收者，我希望邮件失败时看到“备份成功，通知失败”，以便区分数据问题与通知问题。
25. 作为恢复用户，我希望手工下载全部分卷和清单后放入一个目录，以便一次选择完成恢复。
26. 作为恢复用户，我希望缺少任一分卷时程序拒绝恢复并指出文件名，以便避免恢复出损坏数据。
27. 作为恢复用户，我希望哈希不一致时程序拒绝恢复，以便发现下载损坏或被篡改的分卷。
28. 作为恢复用户，我希望程序自动按顺序组装分卷，以便不需要手工操作命令。
29. 作为恢复用户，我希望原始文件恢复到新的时间戳子目录，以便不覆盖现有文件。
30. 作为恢复用户，我希望同名恢复目录已经存在时自动追加编号，以便重复恢复不会失败或覆盖。
31. 作为 MSSQL 备份用户，我希望大型数据库备份同样支持分卷和目录恢复，以便解决同样的上传和下载问题。
32. 作为 MySQL 备份用户，我希望大型数据库备份同样支持分卷和目录恢复，以便解决同样的上传和下载问题。
33. 作为备份用户，我希望“上传后立即删本地包”一次删除完整 ZIP、全部分卷和清单，以便不遗留中间文件。
34. 作为备份用户，我希望自动删除只处理完整备份单元，以便不留下孤儿分卷或清单。
35. 作为备份用户，我希望自动删除一个单元中的部分文件失败时保留清单并记录错误，以便下次可以重试。
36. 作为现有用户，我希望未超限的单 ZIP 和历史未传完记录继续工作，以便升级不影响现有备份。
37. 作为运维人员，我希望日志显示分卷数量、文件统计、上传通道和校验结果，以便定位失败阶段。
38. 作为运维人员，我希望分卷对象位于同一产品前缀和同一任务目录下，以便自动删除不会影响其它文件。
39. 作为产品维护者，我希望规格明确本期不提供云空间下载，以便避免把手工下载流程误实现成新的云 API 集成。
40. 作为产品维护者，我希望“上传分片”和“备份分卷”保持不同术语，以便不混淆包内上传切块与独立备份包文件。

## Implementation Decisions

- 该功能覆盖文件备份、MSSQL 备份和 MySQL 备份；离线介质保持现有行为。
- 文件扫描使用最高层现有的源扫描流程，一次遍历产生可读文件和运行统计，不额外全量扫描源目录。
- 不复制源文件到备份目录。现有压缩流程直接从源读取并写入备份目录，只增加统计、分卷和校验。
- 完整 ZIP 小于等于分卷上限时保留单 ZIP 和现有上传记录结构。
- 超过上限时采用“先完整 ZIP、再字节切卷”策略；完整 ZIP 在所有分卷和清单通过本地校验后删除。
- 分卷是 store 模式的有效 ZIP。每个分卷包含一个原始字节区间 payload 和内嵌清单。
- 分卷目录采用稳定备份标识隔离；完整 ZIP、分卷和清单同属一个备份单元。
- 外部清单文件名包含备份包名，分卷内清单固定为 `manifest.json`。
- 清单记录格式版本、备份标识、任务名、创建时间、分卷上限、完整 ZIP 大小和 SHA-256、发现/打包/跳过文件数、源大小、分卷顺序、payload 大小和 SHA-256、分卷文件大小和 SHA-256。
- 内嵌清单省略承载它的分卷最终包装哈希，避免自引用；靠 payload 哈希仍可完整校验原始数据。
- 全局默认分卷上限为 4 GiB，合法范围为 64 MiB 到 1 TiB。任务值 0 表示继承，正数表示覆盖。
- 设置和三个任务 DTO 增加分卷上限字段；本地数据库增加对应列并支持旧库迁移。
- 结果判定分为数据成功、通知成功和数据失败三类。邮件失败记为 `warn`，不影响任务进入下一轮。
- 发现文件数不等于打包文件数时，即使可读文件上传成功，数据状态仍为失败。
- 失败重试沿用同一个完整 ZIP 或同一个备份单元；源指纹、压缩级别和密码摘要变化时才重新生成。
- 分卷模式在待传记录中保存每个本地文件的网络共享、FTP、云通道状态。重试只处理未完成文件。
- 单 ZIP 模式继续使用原有通道状态，升级后能读取旧记录。
- 上传顺序是全部分卷按编号、外部清单最后。
- 上传后验证远端对象存在和大小。云服务商返回可比较摘要时进行比较；返回服务商专用 ETag 时记录该值并以本地分卷 SHA-256 为内容证据。
- 邮件继续支持原有五个变量，新增文件统计、包统计和大小统计三个组合变量。
- 恢复只读取本地目录，不允许自动从云服务商下载。
- 恢复目录内只允许一组备份标识。多组、缺卷、重复卷、清单版本不支持或哈希不一致时拒绝恢复。
- 恢复优先读取外部清单，缺失时读取分卷内嵌清单。
- 恢复先在临时目录组装完整 ZIP，校验完整 ZIP 的 SHA-256，再安全解压到新的时间戳目录。
- 安全解压拒绝绝对路径、`..` 和越过目标目录的条目录。
- 时间戳目录冲突时追加两位数序号；恢复失败时删除已创建的空/半成品输出目录。
- MSSQL/MySQL 目录恢复先调用同一分卷组装器，再复用现有数据库恢复流程。
- 自动删除、立即删除和云空间清理都按备份单元执行；先删分卷，最后删清单。
- 云对象键增加备份单元目录层级。单 ZIP 继续使用旧对象键，历史包不受影响。
- 不支持旧客户端识别新分卷目录；新客户端负责上传、恢复和清理。

## Testing Decisions

测试只验证外部行为和可观察结果，不依赖私有方法、日志字符串内部实现或具体压缩调用顺序。

采用两个测试接缝：

1. **分卷文件接缝**：直接对完整 ZIP 执行拆卷，再对下载目录执行扫描和组装。验证大小上限、清单往返、缺卷、重复序号、损坏 payload、外部清单缺失时使用内嵌清单、路径穿越拒绝和恢复目录命名。
2. **任务执行接缝**：用临时本机数据库和可替换的上传通道执行文件备份任务。验证发现/打包/跳过统计、单 ZIP 与分卷分支、严格成功判定、逐文件补传、远端校验、邮件统计、立即删除、过期清理和手动目录恢复。

优先复用历史 Core 测试中的纯函数和小型集成测试风格，以及 API 测试中临时数据库和假外部依赖的方式。当前工作树可能缺少部分历史测试文件，执行时只新建本规格需要的测试工程和测试，不恢复无关删除。

UI 只做构建检查和手工验收，不引入新的 WPF 自动化框架。

手工验收至少覆盖：

- 20 MiB 测试文件配合 8 MiB 上限生成多个分卷。
- 下载全部分卷后恢复结果与源文件逐字节一致。
- 删除或修改一个分卷后恢复被拒绝。
- 锁定一个源文件时任务失败且邮件显示跳过数。
- 邮件失败时任务仍按数据成功进入下一轮。
- 自动删除不会留下孤儿分卷或清单。

## Out of Scope

- 客户端直接从云空间下载备份。
- 标准 `.z01`/`.z02`/`.zip` 分卷格式。
- 修改七牛和百度的 4MB 上传分片、续传算法或并发策略。
- 离线介质任务分卷。
- 文件版本浏览、差异备份、增量备份或去重。
- 分卷密码算法变更。
- 云端原子事务删除。
- 新 WPF 自动化测试框架。
- 历史部署文件或其它已删除测试的恢复。

## Further Notes

- 架构取舍已记录在 ADR-0002。
- “分卷”是独立备份包文件；“分片”是上传单个文件时使用的数据块，两者不可混用。
- 外部清单和完整 ZIP 可能同时占本地空间，是“先完整 ZIP、再切卷”的明确代价。
- 实现细节和逐任务执行步骤由后续实现计划承接；本规格只固定产品行为和测试边界。
