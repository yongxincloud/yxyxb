# 未传完备份包复用

**日期：** 2026-10-12  
**状态：** 待审阅。

## 目标

文件备份或数据库备份打出大 zip（约 10GB）后，百度或网络上传失败。失败重试目前会按新时间戳再打包一次，旧 zip 留在本地，百度续传又对不上新路径，磁盘很快被堆满。

未外发完成的包记在任务上。源没有变化时沿用同一个 zip，只补传还没成功的通道。需要新包时，先删掉还没全部传成功的旧包，再打包。

## 已确认

- 文件任务：用源文件的相对路径、大小、修改时间判断有没有变。不算全文件校验。
- 文件任务：指纹、压缩级别、压缩密码都没变，且 zip 还在，则续传，不再打包。变了则先删未传完的旧包，再打新包。
- 库任务（SQL Server 与 MySQL）：上传失败后的重试不重新导出、不重新打包。到本轮截止时间才重新导出。重试窗口里的新数据留到下一轮。
- 范围是文件备份、SQL Server 备份、MySQL 备份。三条外发通道（网络共享、FTP、云）共用同一个 zip。
- 未传完记录放在任务行的 `pending_json`，不放 zip 旁边的清单文件。
- 外发通道都成功之后，下一次计划照常打新包，作为新的还原点。文件内容相同也打新包。
- 邮件失败不重新打包、不重新上传，只重试邮件。
- 磁盘上已经存在、且没有 `pending_json` 的旧 zip 不自动删除。

## 不做

- 媒体备份。
- 新界面、进度条、手动清理按钮。
- 改百度分片大小、续传算法、齐片门闩。
- 自动删除没有未传完记录的历史 zip。
- 恢复仓库里其它已删除的测试文件。只为本规格新增判断测试。
- 在保存任务的对话框里删除 zip。作废发生在下一次执行开始时。

## 未传完记录

`file_tasks`、`mssql_tasks`、`mysql_tasks` 各增加可空列 `pending_json`（TEXT）。空表示没有待续传的包。升级走现有 `SchemaMigrate.Add`。

内容用现有 `JsonUtil` 序列化。文件任务一个包；库任务每个库一个包。

字段：

- `sourceKind`、`sourcePath`：文件任务打包时的源类型和源路径。
- `instanceId`：库任务的实例编号。文件任务不使用。
- `dbNames`：库任务本轮要备份的库名列表（排序后）。文件任务不使用。
- `cycleUntilUtc`：库任务本轮截止时间，格式与现有 UTC 往返字符串一致（`o`）。文件任务为空。单次任务（`once`）为空，表示没有下一轮，一直续传到成功。
- `items[]`：
  - `key`：文件任务固定为 `file`；库任务为库名。
  - `zipPath`：本地 zip 的完整路径。重试必须沿用此路径，百度续传按路径匹配。
  - `fingerprint`：文件任务的源指纹（SHA256 十六进制）。库任务为空。
  - `zipLevel`：打包时的压缩级别。
  - `passwordSha256`：打包时压缩密码的 SHA256（UTF-8，十六进制）。未设密码则为空字符串。不保存密码明文，不写入日志。
  - `networkOk`、`ftpOk`、`cloudOk`：该通道是否已经成功。

指纹只存摘要，不把文件清单写入数据库。计算方式：取 `SourceWalker.WalkLocal` 将要打进包的文件，每行 `相对路径|字节数|最后修改时间Utc.Ticks`，按相对路径序排序，UTF-8 后做 SHA256。相对路径与打包使用同一套。

本轮截止时间只在创建新一代库备份时写入一次：`ScheduleCalculator.NextAfter(周期, 间隔, 本次开始打包的 UTC 时间)`。失败重试不改这个时间。`NextAfter` 返回空（单次任务）时，`cycleUntilUtc` 为空。

三个通道都未启用时，不写 `pending_json`。每次执行都打新包，本地包仍由现有保留天数清理。

## 一次执行

自动调度和「立即执行」使用同一套规则。`MarkResult` 不变：失败则 `现在 + retry_minutes`（小于 1 按 5 分钟），成功则进入下一轮计划。

执行开始时读出 `pending_json`。解析失败视为没有记录，不删除磁盘上对不上的文件。

### 文件备份

1. 按现在的方式准备源。本地和网络共享直接扫描。FTP 仍先下载到临时目录，用来算指纹。
2. 比较源类型、源路径（路径忽略大小写）、指纹、压缩级别、`passwordSha256`。
3. 一致且 zip 文件还在：删除 FTP 临时目录，跳过打包。日志写「沿用未传完的包」和路径。
4. 不一致，或 zip 不在：进入「打新包」。FTP 临时目录留到打包结束，再由现有的 `finally` 删除。

通道：任务当前启用且对应 `*Ok` 仍为 false 的才上传。已经成功的通道不再调用。因此网络共享已成功、云未成功时，下次只传云。执行中途若用户新开一个通道，用同一个 zip 补传该通道。若用户关掉一个通道，该通道不再作为成功条件。

每个通道成功后立刻把对应 `*Ok` 写回 `pending_json`，再继续下一个通道。

### 数据库备份

1. 实例编号或库名列表与记录不一致：整份记录作废，进入「打新包」，本轮全部库重新导出。
2. 当前 UTC 时间已经到达 `cycleUntilUtc`：同样整份作废并重新导出。`cycleUntilUtc` 为空时不因时间作废。
3. 未到截止时间，且每个库的 zip 都在：不连接数据库导出，只补传还没成功的通道。
4. 未到截止时间，库列表没变，但某一个库的 zip 文件不在：只重新导出这一个库并打包，其它库继续沿用。不改 `cycleUntilUtc`、`instanceId`、`dbNames`。

库 zip 的 `fingerprint` 为空。是否沿用由截止时间、实例、库列表和文件是否存在决定。压缩级别或 `passwordSha256` 与当前设置不一致时，整份作废并重新导出。

### 打新包

1. 删除本轮要替换的那些项的本地 zip。同时删除同名的 `.yxypart`。
2. zip 删不掉（占用、权限）：中止本次执行，记录仍指向旧包，不删除百度续传文件，不开始打包。日志写明删包失败。
3. zip 删除成功后，调用云运行时丢掉该路径的百度续传文件。续传文件删不掉只记日志，不阻止打包。已经出现在网盘上的对象不删，留给现有保留天数。新 zip 使用新的时间戳文件名。
4. 从 `pending_json` 去掉已删掉的项并立即保存。
5. 再导出（库）或扫描（文件）并打包。打包完成、zip 文件存在之后，才写入新项。新项三个 `*Ok` 都为 false。整份重新导出时，库任务同时写下新的 `cycleUntilUtc`、`instanceId`、`dbNames`。只补某一个丢失的库时，不改这三项。
6. 打包失败：删除半成品 `.yxypart`，不把半成品写入记录。下次执行重新打包。

这样磁盘上不会同时留下两份待传的大包。打包过程中断后，记录里没有新 zip，下次会重新打包。

### 邮件与结束

通道按上面的规则处理完之后，仍走现有邮件逻辑。

- 启用中的通道还有失败：保留记录，任务失败，下次只补传。
- 启用中的通道都已成功，邮件失败：保留记录（各 `*Ok` 为 true），下次只发邮件。
- 整次执行成功：清空 `pending_json`。勾了「立即删本地包」时，仍按现在的 `DistChannel.Finish` 在成功之后删除。未勾选时，zip 留在备份目录，由现有本地保留天数清理。成功后的下一次计划没有未传完记录，因此会打一个新包。

后续程序仍只在整次成功时运行。

## 失败、改任务、删任务

- 算指纹或准备源失败：本次记失败，不删除已有未传完 zip。
- 只改任务名、软件标识或文件名规则：不作废记录。续传用记录里的完整路径。下次真正打新包时才用新名称。
- 删除文件任务，或删除实例连带删除库任务：先处理记录里的项。是否还要外发，以任务当前启用的通道为准。当前启用的通道里仍有未成功的，删除该本地 zip 和对应百度续传文件。当前启用的通道都已成功，或三个通道都未启用，本地包留在备份目录。有未传完的包删不掉时，不删除任务（删实例时则不删除该实例及其任务），并把失败原因返回给调用方。
- 没有 `pending_json` 的历史 zip 不碰。

日志在这三件事上各写一句原因：沿用、重新打包、删除未传完的包。不写密码和密码摘要。

## 代码落点

| 区域 | 变化 |
| --- | --- |
| `YxyXb.Core` 新类型 | 指纹、记录读写、续传 / 打新包 / 中止 的判断。判断函数不打开数据库、不访问网盘 |
| `SchemaMigrate` | 三张任务表加 `pending_json` |
| 三个任务 Store | 读写该列；删除任务前先按上一节清理 |
| `FileBackupRunner`、`MssqlRunner`、`MysqlRunner` | 先问判断，再打包或补传；每个通道成功后立即保存 |
| `ICloudRuntime` | 增加按本地路径丢弃上传续传的方法。`CloudRuntimeImpl` 对百度调用已有的 `BaiduUploadCheckpoint.Delete`。其它云提供商无操作。Core 不引用百度项目 |
| 任务对话框 | 无改动 |

`Decide` 只返回两种：沿用，或打新包（并给出要替换的项）。它不删除文件。调用方删除这些项；删除失败则中止，不打包。另有一个纯函数：删除成功则可以打包，删除失败则中止。

## 测试

工作区里目前没有测试项目。实现时重建 `tests/YxyXb.Core.Tests`（net48、NUnit，与仓库里原工程一致），只放本规格的判断测试，不恢复其它已删除测试。

1. 指纹相同 → 沿用。一个文件的大小或修改时间变化 → 打新包。
2. 压缩级别变化，或密码摘要变化 → 打新包。源路径或源类型变化 → 打新包，即使指纹碰巧相同。
3. 库任务当前时间早于 `cycleUntilUtc` → 沿用。到达截止时间 → 打新包。`cycleUntilUtc` 为空 → 不因时间打新包。实例或库名列表变化 → 整份打新包。列表相同但其中一个 zip 路径对应的文件不存在 → 只替换该项。
4. `networkOk` 为 true、`cloudOk` 为 false，且任务启用了云 → 结果里只要求补传云。
5. 删除结果为失败 → 中止，不进入打包。删除结果为成功 → 可以打包。

测试用临时文件和内存中的记录，不连接 SQL Server、MySQL 和百度。

## 验收

- 10GB 级文件备份在上传失败后，重试不再产生第二个 zip；百度对同一个本地路径续传，最终上传成功。
- 源文件大小或修改时间变化后，下一次执行先删掉未传完的旧包，再打新包。删除失败时磁盘上仍然只有原来那一份。
- SQL Server / MySQL 任务在本轮截止时间之前的失败重试不再导出。到截止时间后重新导出，且不会留下上一份未传完的本地包。
- 外发成功后的下一次计划生成新的 zip。邮件失败不会多出一个 10GB 文件。
- 启用前已经堆在磁盘上的旧 zip 数量不变，除非用户手工删除，或它们超过本地保留天数后被现有清理删掉。
