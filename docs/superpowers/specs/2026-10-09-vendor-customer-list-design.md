# 厂商客户列表资料与查询

| 项 | 内容 |
| --- | --- |
| **项目** | 用心云·循备 |
| **状态** | 已批准（2026-10-09） |
| **范围** | 厂商端「客户」列表展示客户自填的个人信息和开票信息，并支持关键字查询 |
| **不改** | 看板 `/api/vendor/board`、其它厂商页、客户自己的账号信息编辑页 |

---

## 1. 目标

厂商在客户列表里直接看到客户在「账号信息」里维护的资料，并能按姓名或邮箱等关键字找到人，而不只看到登录邮箱和客户号。

成功标准：

- 打开客户页只显示最近 **50** 条客户（按 `Id` 降序）。
- 搜索框有内容时，在**全部**客户中做包含匹配，最多返回 **100** 条。
- 清空搜索后回到最近 50 条。
- 列表展示全部个人信息和开票字段；未填显示「—」。
- 增加期限、改账号类型、删除之后，按当前搜索条件重新加载列表。

## 2. 方案

客户页的表格改走独立列表接口。账号类型下拉仍用看板里的在售产品。看板继续给其它厂商页用，客户条数上限仍是 200，本次不改。

不把查询塞进看板：每次搜索不应重拉订单、授权、服务商。也不在浏览器里只筛已加载的 50 条，否则搜不到更早的客户。

## 3. 接口

`GET /api/vendor/customers`

未登录厂商：保持现有拒绝方式。

查询参数只有 `q`。服务端自己决定条数，不接受客户端传入的 `take`。

| `q` | 行为 |
| --- | --- |
| 缺省、空、或只有空白 | 最近 50 条 |
| 去空白后有内容 | 全部客户中匹配的记录，按 `Id` 降序，最多 100 条 |

匹配为不区分大小写的包含。命中任一字段即可：

- 客户：`Name`、`Nickname`、`CompanyName`、`CustomerNo`、`InvoiceTitle`、`InvoiceTaxNo`、`InvoiceEmail`
- 账号：`Email`、`Phone`

每行返回表格所需字段：

- 资料：`name`、`nickname`、`companyName`、`phone`、`email`、`invoiceTitle`、`invoiceTaxNo`、`invoiceEmail`、`invoiceLicense`
- 原有操作：`id`、`customerNo`、`directProviderId`、`createdAt`、`status`、`authEndTime`、`productNo`、`productName`、`maxDevices`

`invoiceLicense` 只是客户保存的文件名，不返回文件内容。授权到期日和账号类型口径与看板客户行一致：取该客户 `AuthEndTime` 最晚的一条授权及其产品。

响应形如 `{ ok: true, rows: [...] }`。无匹配时 `rows` 为空数组，HTTP 200。

## 4. 页面

厂商「客户」页表格上方增加一个搜索框和「查询」按钮。回车与按钮相同。`q` 为空时请求不带查询条件。

列顺序：

1. 个人信息：姓名、昵称、公司、手机（同一格，分行）
2. 登录邮箱
3. 客户号
4. 开票信息：抬头、税号、收票邮箱、执照文件名（同一格，分行）
5. 账号类型、归属、注册日、到期日、状态、操作（保持现有行为）

空字符串和 null 都显示「—」。无客户时仍提示先注册再开通。有搜索且无结果时提示「没有匹配的客户」。

## 5. 测试

新增 API 测试：

- 未带 `q` 时只返回最近 50 条，且不含更早的客户。
- `q` 能命中姓名，未命中的客户不出现。
- `q` 能命中登录邮箱和收票邮箱。
- 只有空白的 `q` 与不带 `q` 相同。
- 非厂商请求被拒绝。

页面用现有源码断言测试确认客户页包含搜索框，以及姓名、手机、开票抬头这些字段。
