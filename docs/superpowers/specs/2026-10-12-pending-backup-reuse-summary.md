## 做了什么

大 zip（约 10GB）上传失败后，重试不再按新时间戳重新打包。未传完的包记在任务上，沿用同一个本地路径，只补传还没成功的通道。百度续传因此能对上原文件。

1. **文件备份**：用相对路径、大小、修改时间判断源有没有变。没变就续传；变了，或压缩级别、压缩密码变了，先删掉还没全部传成功的旧包，再打新包。
2. **SQL Server / MySQL**：本轮计划时间之内的失败重试不重新导出。到下一轮计划时间才重新导出。只丢了其中一个库的 zip 时，只补这一个库。
3. **通道**：网络共享、FTP、云各自记成功与否。已经成功的通道不再传第二次。邮件失败不重新打包、不重新上传。
4. **三个通道都没开**：不登记未传完记录，每次仍打新的本地包，靠原来的保留天数清理。
5. **删任务 / 删实例**：还没传完的本地包和对应百度续传文件一起删。删不掉则任务或实例留着，并提示原因。已经传完的本地包留在备份目录。
6. **FTP 源**：下载后按服务器修改时间（MDTM）写本地文件，再算指纹。服务器没有修改时间时，这次中止，不删已有未传完的包。
7. **改任务名后的百度续传**：继续用检查点里原来的远程路径，避免旧的上传编号配到新路径上。
8. **启动数据库**：文件、SQL Server、MySQL 任务表增加 `pending_json`，旧库自动补列，不用手工改表。

## 使用时要注意

- 这次启用前已经堆在磁盘上的旧 zip，程序分不清哪些传到过网盘，**不会自动删**。重复的失败包需要手工删一次。启用之后不再新增。
- 外发全部成功后，下一次计划仍会打一个新包，作为新的还原点。文件没变也会打。
- 删任务时，确认框会说明：还没传完的本地包会删除，已经传完的备份包和日志会保留。
